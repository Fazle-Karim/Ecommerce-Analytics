## 1. Population Funnel

Every metric in this document operates on one of three well-defined
populations. The population used is stated explicitly per metric.

| Population | Definition | Size |
|------------|-----------|-----:|
| **Analytic population** | In-scope status AND in-window AND has item rows | 97,905 |
| **In-scope status** | Status in {delivered, shipped, invoiced, processing, approved}, any date | 98,202 |
| **Full customer base** | All orders, all statuses, all dates | 99,441 |

**Analytic population derivation:**

| Step | Filter | Orders |
|------|--------|-------:|
| 0 | All orders | 99,441 |
| 1 | In-scope status | 98,202 |
| 2 | In-window (2017-01-01 to 2018-08-31 inclusive) | 97,905 |
| 3 | Has at least one row in `order_items` | 97,905 |

Reproducible via `python/order_funnel.py` and pinned in
`documentation/control_totals.json`.

**Default population:** All core revenue, product, seller, and delivery
metrics use the **analytic population** unless stated otherwise.

**Customer-metric note:** §4.1 (Unique Customers) uses the full customer
base for context. §4.4 (Repeat Purchase Rate) uses the **in-scope status**
population. Every metric in §4 states its population explicitly.

## 2. Base Filters

Two ordered filters apply by default to every metric. Boundaries use
half-open intervals (`>=` start, `<` end) so no order is lost at midnight
on the end date.

| Filter | Definition | Rationale |
|--------|------------|-----------|
| **Time filter** | `order_purchase_timestamp >= '2017-01-01'` AND `order_purchase_timestamp < '2018-09-01'` | Half-open interval. 2016 is ramp-up (329 orders); 2018-09/10 has 1 order in-scope. |
| **In-scope filter** | `order_status IN ('delivered','shipped','invoiced','processing','approved')` | Excludes `canceled` (625), `unavailable` (609), `created` (5). Every excluded order has a payment record; the dataset has no refund data; the status indicates the order did not complete. |
| **Delivered filter** | `order_status = 'delivered'` AND `order_delivered_customer_date IS NOT NULL` | Used for delivery and review metrics. Excludes 8 delivered orders with a null delivery date. |

**Default:** unless otherwise stated, a metric uses the **Time filter** and
the **In-scope filter**. Delivery metrics additionally use the **Delivered
filter** and say so.

**Boundary note:** SQL and DAX must use `>= '2017-01-01' AND < '2018-09-01'`.
`BETWEEN '2017-01-01' AND '2018-08-31'` is **incorrect** — it excludes every
order placed after midnight on 31 August.

## 3. Core Metrics

### 3.1 GMV — Gross Merchandise Value (excluding canceled, unavailable, created)

- **Formula:** `SUM(order_items.price)`
- **Source table:** `analytics.fact_order_items`
- **Population:** Analytic population (97,905 orders)
- **Unit:** BRL
- **Pinned value:** `BRL 13,449,529.68`
- **Excludes:** freight, canceled, unavailable, created orders
- **Rationale:** Item price is the revenue attributable to the product sale.
  Freight is tracked separately (§3.4).

### 3.2 Order Count

- **Formula:** `COUNT(DISTINCT orders.order_id)`
- **Source table:** `analytics.fact_orders`
- **Population:** Analytic population
- **Unit:** integer
- **Pinned value:** 97,905

### 3.3 AOV — Average Order Value

- **Formula:** `GMV ÷ Order Count`
- **Population:** Analytic population
- **Unit:** BRL

### 3.4 Freight Charged

- **Formula:** `SUM(order_items.freight_value)`
- **Source table:** `analytics.fact_order_items`
- **Population:** Analytic population
- **Unit:** BRL
- **Pinned value:** `BRL 2,234,177.06`
- **Note:** Tracked as a separate measure, never rolled into GMV.
  Not labeled "revenue" — no cost data exists to determine margin.

### 3.5 Total Customer Paid

- **Formula:** `GMV + Freight Charged`
- **Population:** Analytic population
- **Unit:** BRL
- **Pinned value:** `BRL 15,683,706.74`
- **Reconciliation:** Matches `SUM(payments.payment_value)` on the same
  population to within `BRL 2,762.33` net (0.0176%) and `BRL 3,033.13`
  absolute (0.0193%).

### 3.6 Items per Order

- **Formula:** `COUNT(fact_order_items rows) ÷ COUNT(DISTINCT orders.order_id)`
- **Population:** Analytic population
- **Unit:** decimal

## 4. Customer Metrics

All customer metrics use **`customer_unique_id`** as the customer key — never
`customer_id`. Rationale in `data_quality_log.md` §3.

**Population note:** §4.1 uses the full customer base (all statuses, all
dates) for context. §4.2 and §4.3 use the analytic population for
period-scoped definitions. §4.4 uses the **in-scope status** population,
consistent with the GMV rule. Every metric below states its population.

### 4.1 Unique Customers

- **Formula:** `COUNT(DISTINCT customer_unique_id)`
- **Population:** Full customer base — all dates, all statuses
- **Unit:** integer
- **Pinned value:** 96,096

### 4.2 New Customers

- **Definition:** A customer whose first-ever order falls inside the current
  period, using the **analytic population** as the source of orders.
- **Formula:** `COUNT(DISTINCT customer_unique_id)` where
  `first_order_date >= period_start AND first_order_date < period_end`
- **Population:** Analytic population
- **Note:** "First-ever" is computed across the customer's full order
  history. The definition of "order" uses the analytic population's
  status filter.

### 4.3 Returning Customers

- **Definition:** A customer who placed an order in the current period and
  had at least one prior order before the period start, using the analytic
  population.
- **Formula:** `COUNT(DISTINCT customer_unique_id)` where
  `first_order_date < period_start` AND customer has an order in the
  current period
- **Population:** Analytic population

### 4.4 Repeat Purchase Rate

- **Formula:** `(Repeat customers) ÷ (Total unique customers)`
  - Repeat customers: `COUNT(DISTINCT customer_unique_id HAVING >1 order)`
  - Total unique customers: `COUNT(DISTINCT customer_unique_id)`
- **Population:** **In-scope statuses only** — all dates, but only
  orders whose status is in {delivered, shipped, invoiced, processing,
  approved}. Consistent with the GMV rule (§3.1), a canceled order is not
  a purchase and does not count toward repeat activity.
- **Unit:** percentage
- **Pinned value:** **3.04%** (2,887 of 94,986)

> **Alternative figure (full base):** If repeat rate is computed over
> **all statuses** (including customers whose only additional order was
> canceled, unavailable, or created), the value is **3.12%** (2,997 of
> 96,096). This figure is documented in `control_totals.json` for
> reference only. The reported figure is 3.04%, because the report uses
> one figure and that figure must be consistent with the GMV rule.

### 4.5 RFM Segments

- **Population:** Analytic population (97,905 orders), further restricted
  to orders with `order_purchase_timestamp < '2018-09-01'` for recency.
  No orders after 2018-08-31 enter RFM, so recency never goes negative.
- **Recency:** Days between a customer's most recent order (on or before
  2018-08-31) and the RFM snapshot date, **2018-08-31**. Lower is better.
- **Frequency:** Count of distinct orders per `customer_unique_id` within
  the analytic population. Because 96.9% of customers have exactly one
  order, frequency is **rule-based, not quintile-based**:
  - 1 order → band "1"
  - 2 orders → band "2"
  - 3+ orders → band "3+"
  NTILE is not used for frequency — ties would be split arbitrarily.
- **Monetary:** Sum of GMV per `customer_unique_id`, binned into quintiles.
- **Recency scoring:** Quintiles of the recency distribution (5 = most recent).
- **Segment rules:** To be defined after inspecting the score distribution
  in Step 4.

## 5. Time Intelligence

### 5.1 Time Axis

- **Column:** `order_purchase_timestamp`
- **Granularity:** Month and Year
- **Time zone:** as stored

### 5.2 YoY Comparison Window

- **Current period:** `>= '2018-01-01' AND < '2018-09-01'`
- **Prior period:** `>= '2017-01-01' AND < '2017-09-01'`
- **Rationale:** Only Jan–Aug is comparable — 2018-09/10 is incomplete, and
  2017-11/12 has no 2018 counterpart.
- **Reporting language:** "Jan–Aug comparison", never just "YoY".

### 5.3 MoM Growth

- **Formula:** `(current_month_value − prior_month_value) ÷ prior_month_value`
- **Population:** Analytic population
- **Note:** Partial months are excluded from MoM charts.

### 5.4 Rolling 12-Month

- **Formula:** `SUM` over trailing 12 months from the current period end
- **Note:** The first full rolling-12-month window ends in **2017-12**
  (needs 12 complete months starting 2017-01).

## 6. Delivery & Satisfaction Metrics

All metrics in this section use the **Delivered filter**:
`order_status = 'delivered'` AND `order_delivered_customer_date IS NOT NULL`,
plus the **Time filter** and **In-scope filter**.

**Late-rate denominator = 96,203 orders** (pinned in `control_totals.json`).

### 6.1 Delivery Time

- **Formula:** `DATEDIFF(day, order_purchase_timestamp, order_delivered_customer_date)`
- **Unit:** days
- **Note:** Only rows with both dates present are counted.

### 6.2 Late Order

- **Definition:** An order delivered after its `order_estimated_delivery_date`.
- **Comparison:** **Date-only** — both sides normalized to midnight before
  comparison. `order_estimated_delivery_date` is always midnight (verified:
  0 of 99,441 rows have a non-midnight time). Raw timestamp comparison
  misclassifies 1,292 orders.
- **Flag:** `1` if `DATE(order_delivered_customer_date) > DATE(order_estimated_delivery_date)`, else `0`
- **Unit:** binary

### 6.3 Late Order Rate

- **Formula:** `(Late orders) ÷ (Delivered orders with non-null delivery date)`
- **Population:** Delivered filter + Time filter + In-scope filter
- **Denominator:** 96,203
- **Pinned value:** **6.79%** (6,531 late orders).

> **Note:** An all-dates figure (6.77%) exists in earlier drafts. Only the
> in-window figure is reported.

### 6.4 Average Review Score

- **Formula:** `AVG(reviews.review_score)`
- **Source table:** `analytics.fact_orders` joined to deduplicated reviews
- **Population:** Delivered filter + Time filter + In-scope filter + review present
- **Unit:** decimal (1.0–5.0)
- **Note:** Computed over reviewed orders only. Orders without any review
  (768 total, all statuses) are excluded — not counted as 0.

### 6.5 Late vs On-Time Review Gap

- **Formula:** `AVG(review_score for late orders) − AVG(review_score for on-time orders)`
- **Population:** Delivered filter + Time filter + In-scope filter + review present
- **Unit:** decimal points
- **Pinned values:** late = **2.27**, on-time = **4.29**, gap = **−2.02**

## 8. Comparison Rules

### 8.1 Like-for-Like

Any comparison (YoY, MoM, region vs region) uses the **same population and
same date range** on both sides. Mixing populations is a bug.

### 8.2 Population Consistency

Any two numbers appearing in a comparison must come from the same
population. If they don't, the difference is a population mismatch, not a
result. `reconcile_payments_v2.py` enforces this with an assertion.

### 8.3 Denominators

Every percentage in the report states its denominator — in the label, the
tooltip, or the accompanying text.

### 8.4 Rounding

- Currency: 2 decimals
- Percentages: 2 decimals
- Averages: 2 decimals
- Counts: integers only
- **Reconciliation comparisons:** round both sides to cents before
  subtracting, so floating-point noise does not appear as a residual.

### 8.5 Currency Formatting in Markdown

Currency values in markdown files use `BRL` or are wrapped in backticks:
`` `BRL 273,345.09` ``. This prevents GitHub from rendering `$` as math.

## 9. Known Exclusions

| Exclusion | Count | Reason |
|-----------|------:|--------|
| Canceled orders | 625 | Payment record exists; dataset has no refund data; status indicates the order did not complete |
| Unavailable orders | 609 | Same as above |
| Created orders | 5 | Same as above; all 5 have a payment row |
| Orders before 2017-01 | 296 (in-scope) | Ramp-up period |
| Orders on/after 2018-09 | 1 (in-scope) | Incomplete tail |
| Delivered orders with null delivery date | 8 | Late rate only; kept in order count |
| Orders with no review | 768 | Review score only; excluded from avg review |

**Total exclusions from raw to analytic population:** 99,441 − 97,905 =
**1,536 orders (1.54%)**.
