## 1. Dimensions

| Dimension | Grain | Rows |
|-----------|-------|-----:|
| `analytics.dim_date` | One row per calendar day, 2016-01-01 .. 2018-12-31 | 1,096 |
| `analytics.dim_customer` | One row per `customer_unique_id` in analytic population | 94,703 |
| `analytics.dim_product` | One row per `product_id` appearing in analytic fact_order_items | 32,578 |
| `analytics.dim_seller` | One row per `seller_id` appearing in analytic fact_order_items | 3,029 |

All dimensions use **integer surrogate keys** as primary keys, keeping the
natural keys (`customer_unique_id`, `product_id`, `seller_id`, `full_date`)
as columns.

### dim_date flags

| Flag | Definition |
|------|-----------|
| `is_in_window` | 2017-01-01 .. 2018-08-31 (608 days) |
| `is_complete_month` | Same as `is_in_window` — excludes 2016 ramp-up, 2018-09, 2018-10 |
| `is_jan_aug` | Jan through Aug, regardless of year (486 days) — for like-for-like YoY |

`date_key` is `yyyymmdd` as an integer.

### dim_customer tie-break

A single `customer_unique_id` can appear under multiple zip prefixes when
they moved between orders. `dim_customer` uses the **latest purchase wins**
rule: for each customer, the row with the most recent
`order_purchase_timestamp` supplies the zip, city, and state. Ties broken
by `customer_id ASC` for determinism.

**240 customers** in the analytic population have more than one distinct
zip. This is logged in the decision log.

### Geography

There is **no `dim_geography`** — city, state, and coordinates are
denormalized directly into `dim_customer` and `dim_seller`.

City and state come from the customer and seller files themselves, not
from geolocation. Coordinates come from a `LEFT JOIN` to
`clean.geolocation` by zip prefix.

Coverage:

| Dimension | Rows with NULL coordinates |
|-----------|---------------------------:|
| `dim_customer` | 264 |
| `dim_seller` | 7 |

The 264 customers and 7 sellers have zip prefixes that do not appear in
the geolocation table, or belong to the 4 prefixes with all coordinates
outside the Brazil bounding box.

## 2. Facts

| Fact | Grain | Rows |
|------|-------|-----:|
| `analytics.fact_orders` | One row per analytic order | 97,905 |
| `analytics.fact_order_items` | One row per item in analytic orders | 111,752 |
| `analytics.excluded_orders` | One row per non-population order | 1,536 |

### Identity

    fact_orders (97,905) + excluded_orders (1,536) = 99,441 (raw order count) ✅

### Exclusion reasons

| Reason | Count |
|--------|------:|
| `out_of_scope_status` (canceled / unavailable / created) | 1,239 |
| `out_of_window` (outside 2017-01-01 .. 2018-08-31) | 297 |

### fact_orders columns

- Surrogate key `order_key`
- FKs: `customer_key` → dim_customer, `date_key` → dim_date
- Natural keys: `order_id`, `customer_id`, `customer_unique_id`
- Status + all timestamps
- `delivery_days` = DATEDIFF(day, purchase, delivered_customer), NULL if not delivered
- `is_late` = 1 if DATE(delivered_customer) > DATE(estimated_delivery) AND status = 'delivered' AND delivered_customer IS NOT NULL
- `review_score` from deduplicated `clean.reviews`, or NULL if no review
- `payment_total` = SUM(payment_value) per order, or NULL if no payment (the one missing-payment order)
- `item_count` = number of items in the order
- `seller_count` = distinct sellers in the order

### fact_order_items columns

- Surrogate key `order_item_key`
- FKs: `order_key` → fact_orders, `product_key`, `seller_key`, `customer_key`, `date_key`
- Natural keys: `order_id`, `order_item_id`, `product_id`, `seller_id`
- `price`, `freight_value` at item grain
- `flag_shipping_limit_anomaly`
- **Copied from order grain:** `is_late`, `review_score`, `order_status`

**Aggregation rule:** the three copied attributes MUST be aggregated at
order grain (DISTINCTCOUNT(order_id) or AVERAGEX(VALUES(order_id), ...)),
never with a plain AVG(). Multi-item orders would otherwise be
over-weighted. This rule is documented in the fact table header and in
`metric_definitions.md`.

### No relationship between fact tables

There is **no foreign key between `fact_orders` and `fact_order_items`**.
Both connect directly to the shared dimensions. This avoids ambiguous
filter paths in Power BI when a visual filters by both fact tables.
